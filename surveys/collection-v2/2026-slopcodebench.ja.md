# SlopCodeBench：反復開発でAI生成コードの品質はどう劣化するか

## 要点

AIの完了報告やテスト通過率だけでは、変更を重ねたコードの保守性を判断できない。本論文は、自分で作ったコードを継続して拡張する条件で、機能の正しさと構造的な品質を別々に測定する。品質を指示するプロンプトにも一定の効果はあるが、劣化の解消や機能の正しさとの両立が実証されたわけではない。

本記録は単一論文のサーベイと、既存記録との比較・考察であり、網羅的なシステマティックレビューではない。

## 2. 研究課題と位置づけ

問いは「いまの要件を満たせるか」に加えて、「初期の設計判断を引き継ぎながら後続要件に対応できるか」である。単発のバグ修正評価では、局所的には動くが次の変更を難しくする設計を見落としやすい。人間が設計した成熟リポジトリを各段階の出発点にすると、エージェント自身の設計判断の累積を切り離してしまう。

そこで本研究は、外部から観測できるCLI/API契約のみを与え、内部設計はエージェントに任せる。後続段階へ自身のワークスペースを引き継がせ、正しさと品質の推移を追う（§1–2）。

## 3. 手法・データ・比較条件

36問題、計196チェックポイントを用意し、各問題を3–8段階で拡張する。初期状態は空で、各段階では前段階のコードと新しい仕様を入力する。過去の会話は引き継がない。評価用テストとそのフィードバックは非公開であり、通常のCI結果を参照しながら修正する開発とは条件が異なる。

仕様は言語非依存だが、今回の実験はPythonのみ。15モデルを各種CLIハーネスで評価し、非rootのDockerコンテナで作業ディレクトリだけを段階間で維持する。インストール済みパッケージ、シェル履歴、セッション状態はリセットする。各runに2時間の実時間制限があり、turn数・費用の上限は設けない（§3、付録C）。**モデル単体を同一ハーネスで比較した実験ではない。**

評価を次のように区別する（§2.4）。

| 指標 | 成功条件・集計単位 |
|---|---|
| Strict | 当該チェックポイントの全テスト。過去段階の回帰テストを含む |
| Isolated / ISO | 当該段階の非回帰テストをすべて通過 |
| Core | 仕様に明記・例示された主要機能のテストのみを通過 |
| Partial | 問題内で少なくとも1チェックポイントをStrictで解決 |
| 問題の完全解決 | その問題の全チェックポイントを解決 |

Strict/ISO/Coreの分母は固定の196チェックポイント。中断後の未実行段階は不成功に数える。一方、品質指標はコードが出力された段階だけを対象とする。この分母の違いにも注意が必要である。

### 品質指標

**Structural erosion（構造劣化）**は、複雑な関数への複雑性の集中を測る。各関数の重みを次で定義する。

`mass(f) = CC(f) × sqrt(SLOC(f))`

全関数のmassのうち、循環的複雑度CCが**10を超える**関数に属する割合をErosionとする。単なる行数やCCの平均ではない（§2.3、式2–3）。

**Verbosity（冗長性）**は、137個のAST-grepルールで検出した行と構造的クローン行の和集合をLOCで割った値である。複数ルールに該当する行は重複計上しない（式4）。どちらも保守性を測る代理指標であり、セキュリティ、可読性、実際の保守工数全体を直接測るものではない。

## 4. 結果と根拠

### 4.1 正しさと費用

| モデル・Table 1の設定 | Strict (%) | ISO (%) | Core (%) | USD/チェックポイント |
|---|---:|---:|---:|---:|
| GPT 5.5 | 14.8 | 28.1 | 66.8 | 1.51 |
| GPT 5.3 Codex | 11.2 | 26.0 | 60.7 | 0.66 |
| GPT 5.4 | 10.7 | 23.5 | 62.8 | 0.72 |
| Opus 4.6 | 9.7 | 20.9 | 67.3 | 3.17 |

出典：§3、Table 1の抜粋。モデルごとのbest just-solve runであり、現行製品の価格表や一般的な実務ランキングではない。

全36問題のうち、全段階を完全解決できた問題はどの構成でも0。最高の14.8%は**チェックポイントのStrict成功率**で、問題の完全解決率ではない。段階の開始から終了にかけて平均費用は2.2倍となった（§3.1）。

### 4.2 品質の変化とOSS比較

- 構造劣化は軌跡の77%、冗長性は75.5%で増加した（§3.2）。
- 473件のPython OSS、計13,667コミットを比較対象とした。Table 2では、人間側HEADの平均が冗長性0.19・構造劣化0.34、エージェント側2,869チェックポイントの平均が0.44・0.68で、比率は約2.3倍・2.0倍（§3.3）。
- 人間側の1コミットとエージェント側の1チェックポイントは作業量や課題難度を統制した同一単位ではない。比率をそのまま「人間より保守コストが何倍」と解釈できない。
- 2024年前後のOSS比較は観察的分析であり、各コミットのAI利用有無を識別した因果推定ではない。

### 4.3 プロンプト介入

禁止したい冗長表現などを列挙するanti-slopと、計画を先に作らせるplan-firstを比較した（§3.4、Table 3）。例えばGPT 5.5のanti-slopでは、Erosionは0.49→0.21、Verbosityは0.32→0.21へ低下した一方、Strictは14.8%→9.2%、費用は1.51→1.68 USD/チェックポイントとなる。

品質指標の改善だけで全体の成功を判断してはいけない。介入2種の平均費用増は本文で12.1%と報告されるが、劣化傾向の一般的な解消には至っていない。§3.4はGPT 5.4のanti-slopに開始から終了まで改善する例外があったとも述べるため、「すべての軌跡で必ず悪化する」とはしない。

### 原文内の不整合・未解決事項

- §3.1はCore最高67.3%をOpus 4.5と記すが、Table 1はOpus 4.6が67.3%、Opus 4.5が57.7%。本記録は表の値を採用する。
- 導入部の介入による正しさ低下2.3ポイントと、§3.4のStrict平均低下2.4ポイント（anti-slop）・3.6ポイント（plan-first）は一致しない。Table 3のモデル別値を優先し、単一の総平均にまとめない。
- 要旨の品質改善「最大約3分の1」と、本文の指標・条件別のより大きな改善幅は同じ集計ではない。開始時の値、全段階平均、介入種類を区別して確認する必要がある。
- Table 7にはTable 1で評価されたOpus 4.7とGPT 5.5の行がなく、その表だけでは全モデルのハーネス版を確定できない。

## 5. 関連研究との比較・横断的考察

| 観点 | SlopCodeBench | 既存の[SWE-Journey記録](2026-swe-journey.ja.md) |
|---|---|---|
| 中心的な問い | 自身の設計が反復拡張時の品質にどう影響するか | 模擬利用者との長期対話で機能実装・維持がどう変わるか |
| 状態・対話 | コードを維持、段階ごとの会話はリセット | 模擬利用者との対話を含む長期開発 |
| 主な測定軸 | Strict/ISO/Coreと構造劣化・冗長性 | 要求機能・既存機能のテスト通過と対話行動 |
| 併用の意義 | 機能テストで見えにくい構造的な負債を観測 | 要件伝達・受入確認を観測 |

比較は既存の部分読了記録に基づく概念整理で、同条件の再評価ではない。タスク・テスト・集計単位が異なるため成功率の直接比較は行わない。

本サーベイの考察として、両者を合わせると、**要件の受入確認**と**コード構造の継続観測**を別の評価軸にする意義が見える。ただしSlopCodeBenchは「構造劣化が失敗の原因」とする要因を独立操作した実験ではなく、両者の関係を因果として断定できない。リファクタリング専用工程や独立レビューの有効性も、今回の実験では確かめていない。

## 6. 限界と妥当性への脅威

1. **一般化**：著者作成の36問題とPython実装の結果であり、既存の巨大システム、他言語、通常のCIフィードバック付き開発へそのまま適用できない。
2. **指標の構成**：ASTルールの価値判断、クローン検出、CC閾値に依存する。必要な重複やドメイン固有の複雑さもあり、値を機械的に最小化すると正しさを損なう可能性がある。
3. **人間比較**：OSSは成熟度・作業単位・選択過程が異なり、AI支援の混入もあり得る。「純粋な人間対AI」の統制実験ではない。
4. **構成差**：モデル、ハーネス版、推論設定が混在する。現行バージョンの製品能力を推定するには再測定が必要。
5. **欠測と再現性**：中断を不成功に数える正しさと、出力がある段階だけの品質では母集団が違う。本サーベイでは試行分散や配布コードとの一致を独立検証していない。
6. **本文の不整合**：前節の表・本文の差異が残り、集約値の再計算なしに解消済みとはしない。

## 7. 無料で始める検証案と実務への応用

以下は本リポジトリの独自提案で、未実施。

1. 公開可能な小さなPython CLIを対象に、将来仕様を先に見せず4段階で機能を追加する。仕様、初期コード、使用モデル・ハーネス版、設定を固定して記録する。
2. 有料APIを追加購入せず、既存の実行枠またはローカルモデルで予備試行する。ハードウェア・電力などの費用までゼロになるという意味ではない。
3. 段階ごとに新規機能・回帰テスト、CC分布、変更行数、重複行を記録する。論文の137ルールと同じ実装を確認するまでは「SlopCodeBench Verbosity再現」と呼ばず、代替指標と明記する。
4. 通常条件と品質ガイダンス条件を比べ、余力があれば構造レビューを挟む条件を追加する。改善を前提にせず、機能成功率・品質変化・所要時間・費用を同時に見る。
5. 少数回の結果はケーススタディとし、モデル優劣や施策効果を一般化しない。将来の本格追試では複数run・事前に定めた分析方法を用いる。

運用へ応用する場合は、PRごとに「要求を満たすか」と「既存の複雑な関数へ分岐を集中させていないか」を別々にレビューする案が考えられる。単に「簡潔に書く」と指示するだけで品質保証が済むとは扱わない。
