# Claude Codeで業務ノウハウを公開するときの漏えい経路

- [原文：記事は読み返しても、git の名義は読み返さない](https://zenn.dev/pepe_3_go/articles/claude-code-article-leak-paths)、いわい ゆう、2026年10月26日。
- 種別：個人の実践記事。論文ではない。本文確認、独立検証・再現未実施。
- 筆者の検証環境：Windows 11、Claude Codeデスクトップ、Teamプラン。

## 7行でつかむ

1. 業務で使ったClaude Codeのセッションから記事を書くと、客先名や案件情報が下書きに混じり得る。
2. 筆者は漏えい経路を、本文・コード・画像・Gitメタデータの4つに分けて点検する。
3. 本文やコードは非公開のNGワード表でチェックし、業務コードは公開用の最小例に書き直す。
4. 画像はファイル名や顧客デザインの映り込みを人が確認する。
5. Gitではコミットのメールアドレスやpushに使うアカウントも確認する。
6. 取引先一覧にもなるNGワード表や根拠メモは、公開用リポジトリの外に保管する。
7. 実務では会社の公開承認、差分・画像・履歴の確認を組み合わせ、最後の公開判断を人が持つ。

## 背景と対策

筆者は会社のメールアドレスがコミットに入ったため履歴書き換えが必要になった経験を紹介する。公開用リポジトリのローカルGit設定に記事用名義とnoreplyメールアドレスを設定し、履歴を点検する。また複数の認証情報があるPCでは、意図したアカウントで認証しているか確認する。

業務コードには識別子や権利上の問題が残りうるため、筆者は最小例を新たに作る。スクリーンショットは目視し、記事の公開操作は人が判断する。NGワード表も顧客リストなどの機密になりうる。

## 会社での適用案（未実施）

- 公開可否、知的財産、契約、顧客情報、画像に関する社内ルールと承認経路を確認する。
- 公開用の作業領域を分け、実データや業務セッションの記録を持ち込まない。
- 本文・コード・画像・メタデータ・履歴・送信先を人が確認する。自動検査は表記揺れや未知の機密、画像を見落としうる。
- Git設定の適用元と履歴のauthor・committerを確認し、GitHubの認証アカウントも別途確認する。名義は会社の規程に従う。
- 漏えい時は会社のインシデント手順に従う。履歴書き換えは複製・キャッシュ・通知済み情報の回収を保証しない。

## 限界

単一ユーザーの事例であり、NGワード照合や手動レビューの完全性は実証されていない。Gitの作者情報とGitHub認証は別の仕組みであり、リモートURLのユーザー名だけで認証先の正しさは保証されない。
