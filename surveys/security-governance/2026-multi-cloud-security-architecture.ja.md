# AWS・Azure・GCPを横断するマルチクラウド・セキュリティアーキテクチャ

## 概要

- **何について**：クラウド事業者を横断するセキュリティ設計を提案した学術誌掲載論文。
- **何を述べるか**：ID・分離・データ保護・監視・ポリシーの統制を揃える。
- **留意点**：検証結果の報告には、再計算可能な定量的証拠が不足している。

## 問い・方法・証拠

異なるクラウド統制の間で、共通のセキュリティ意図をどう維持するか。提案はID連携、サービスメッシュによる分離、独立した鍵管理による暗号化、SIEM／SOAR統合、policy-as-codeを組み合わせる。§6はIaaSテストベッドでの構成監査と模擬攻撃を、クラウド別の統制と比較したと説明し、ポリシー不整合リソースと対応不要アラートの減少を主張する。[M2 §§5–6]

## 批判的考察・妥当性

証拠の点検：検証節には、比較前後の件数、検知遅延の実測値、標本数、反復試行、不確実性の推定が示されていない。確認した論文内に、デプロイ可能な設定や実験リポジトリは見つからなかった。そのため、改善率や統計的有意性は再計算できない。要旨の強い検証表現を、独立に確立された効果量として読むことはできない。[M2 要旨、§§6–7]

本サーベイの設計上の評価では、統制目標の一覧として使える一方、具体的なクラウドへの対応づけには改めて公式資料の確認が必要である。図の「同じロール」から、実効権限の同等性を仮定しない。

| 本サーベイの設計点検案 | 採用前に必要な証拠 |
|---|---|
| IDの意味 | 人／ワークロードの区別、クレーム対応、トークンのaudience、拒否テスト |
| ポリシーの同等性 | 実効権限、例外、階層の扱い |
| 制御プレーンの障害 | IdP・鍵管理・ログ転送・対応処理が失敗するシナリオ |
| 分離の適用範囲 | 強制点を通る通信と迂回する通信 |
| 検知品質 | 正解ラベル付きイベント、ログ欠落、見逃し、端から端までの時刻 |

これらは点検要件の提案であり、論文の構成で検証済みの機能ではない。集中化は点検を簡単にする可能性と、管理権限を集中させる可能性がある。復旧と影響範囲を明示的に評価する。サービスメッシュの導入だけで、全クラウドアクセス経路の受入条件を満たしたことにはしない。
