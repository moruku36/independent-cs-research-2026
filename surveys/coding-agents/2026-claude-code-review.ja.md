# Claude Codeチームのコードレビュー：AI時代の多層防御

- 種別：企業の技術記事・実務事例（査読論文ではない）

## 7行でつかむ

1. AIエージェントが大量の変更を作る開発で、Claude Codeチームがどう品質を守るかを説明する企業事例。
2. 実装中のテスト、AIによるバグ・セキュリティレビュー、CI、人間の承認、段階リリースを重ねる。
3. 変更のリスクに応じて人間の承認人数を変え、重要な領域には人の確認を残す。
4. 2026年6〜9月に、同チームではマージされたPR数が2倍超になり、revertされたPRの割合は40％超低下したと報告。
5. これは同社の観察結果であり、各施策が改善を引き起こしたとは証明されていない。
6. 実務ではまず小さなリポジトリで、テスト・リスク・戻し方をPRに明記し、AIレビューと人の判断を組み合わせる。
7. レビュー時間だけでなく、差し戻し率や障害、誤検知、レビューの反復回数も見て、安全性と負担を両立させる。

## 問題設定と結論

コードレビューの目的は、出荷前に問題を発見することと、チーム内にコードの理解を広げること。著者らは、すべての差分を人が読むことを目的にせず、どの故障をどの検査が見つけるかを考える。人の時間を節約しても障害対応が増えれば意味がないため、revertとインシデントを安全性の指標に置く。

## 提案されたレビューの流れ

1. **PR前**：テストやビルド、UIなら画面確認など実行可能な検証手段を与え、出力を確認。別コンテキストのエージェントで差分を再確認する。
2. **AIレビュー**：変更の目的と周辺コードを照らし、複数エージェントによる発見と別グループの検証でノイズを抑える。指摘には修正か理由付きの解決が必要。
3. **セキュリティとCI**：専用レビュー、lint、型チェック、テスト、ビルドをゲートにする。PRにはテスト方法と戻し方を記す。
4. **リスク別の承認**：低リスクは条件付きで人の承認なし、中リスクは1人、高リスクは2人。軽い経路は信頼された作者に限定し、機微領域やCIには人を残す。AIの承認は人の承認に数えない。新しいコミットに対して承認の再確認が必要になる場合がある。
5. **マージ後**：マージキューで統合後のチェックを再実行し、フラグ・社内利用・段階リリースを使う。監視と迅速な切り戻しを最後の防御にする。

## レビューを改善する仕組み

過去の障害・revertを評価セットにし、レビューの見逃しや誤検知を継続評価する。AI同士の修正と再レビューが延々と続く問題に対し、3ラウンド後に方針を見直し、その後は新しい差分を中心に確認し、既出指摘の繰り返しを避ける。記事はあるPRで50回超のレビューが発生した例も挙げる。

人が全部の差分を読まないと共有知識が薄れる。チームは必要な部分をAIに解説させ、オープンな作業チャンネルでも文脈を共有するが、記事自身は形式的な知識共有の仕組みはないと述べる。生成された説明の正しさや変更理由は別途確認が必要。

## 実務への適用案（未実施）

- PRテンプレートに「目的・テスト結果・リスク・切り戻し」を設け、認証・課金・CI・デプロイなどは人の承認を必須にする。
- まず1リポジトリでAIレビューを試し、実際の誤検知と見逃しを短いレビュー指示と評価事例に反映する。
- レビュー待ち時間・人の承認数と併せ、差し戻し率・障害率・指摘の妥当性を同じ期間で記録する。
- 自動マージは事故対応・権限管理・ロールバックを確認した上で低リスクから検討する。記事の条件をそのまま一般化しない。

## 限界と関連項目

数値は社内の自己報告で、対照群・変更の種類・測定定義などが十分に示されず、因果関係や他組織への再現性は不明。高いテスト網羅、CI、安全性レビュー、社内利用、リリース基盤がある環境の事例である。記事では自動的に承認条件を厳格化する仕組みはまだないとも記す。
